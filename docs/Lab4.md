# Lab 4 - Network Monitoring with Observium

This laboratory assignment covers the protocols that monitor network devices, and a network management system (NMS) that uses them. In Part A you work with the protocols themselves: SSH, NTP, and SNMP (versions 2c and 3). In Part B you use Observium, a network management platform that supports a wide range of device types. Observium is a good, yet simple, example of an NMS that has many of the features discussed in the course. More information on Observium is available at: [https://www.observium.org/](https://www.observium.org/)

You will rely entirely on netlab and Ansible to configure the network device. Your will decide the settings, apply them with the provided Ansible playbooks, and then verify, observe, and explain what the devices and the NMS do with them. You may log in to a device to run show commands.


# Lab Objectives

The objectives of this lab are:

- Configure and verify SSH, NTP, and SNMP on devices using Ansible.
- Verify protocol operation and diagnose issues.
- Deploy Observium and integrate devices via SNMP.
- Explore Observium's interface and key features.
- Add devices and configure discovery settings.
- Run network discovery to identify devices and topology.
- Create and manage custom alerts.
- Filter and analyze event logs.
- Differentiate SNMP polling from traps.
- Explore the device, neighbour, and network data an NMS builds, including topology and traffic maps.
- Report configurations, verification results, and challenges.

## Task 2: NTP

Objective: synchronize the clocks of the devices with a time source.

Without correct time setting and synchronization on networks, the time on individual devices will slowly drift away from each other at varying degrees until potentially each has a significantly different time. In network management systems and security systems that rely on ordered logging of events, this can be a real problem as events generated by a device may be received in a different order than the actual order of occurrence.

The workstation needs to be configured as an NTP server. This task sets the time zone of the routers and points them at that server.

1. Install the NTP service and check its status on the workstation and note the clock source

   ```bash
   sudo apt install chrony -y
   systemctl status chrony
   ```

2. You may also need to set the local time zone and note the time:

   ```bash
   sudo timedatectl set-timezone America/Halifax
   date
   ```

3. Check the current clock of the routers.

   ```bash
   ansible all -m arista.eos.eos_command -a "commands='show clock'"
   ```

4. Review the `ntp` section of `mgmt_vars.yml`. The time zone is the local Atlantic time zone. The NTP server is the workstation.

5. Apply the NTP settings to all routers.

   ```bash
   ansible-playbook ../mgmt/play_config_mgmt.yml --tags ntp
   ```

6. Check the clock again. It should show local time. Then verify the synchronization. The status may remain unsynchronized for a long time, so you may want to come back to this later.

   ```bash
   ansible all -m arista.eos.eos_command -a "commands='show clock'"
   ansible all -m arista.eos.eos_command -a "commands='show ntp status'"
   ansible all -m arista.eos.eos_command -a "commands='show ntp associations'"
   ```

7. Look at the configuration lines that the play added.

   ```bash
   ansible r21 -m arista.eos.eos_command -a \
       "commands='show running-config section ntp|clock'"
   ```

## Task 3: SNMPv2c

Objective: enable SNMP on the devices, and use it from the workstation.

SNMP is a widely used protocol for managing and monitoring networks. Most of the enterprise grade network devices support SNMP. SNMP agents on these devices must be enabled and be configured to communicate with the network management system. The community strings `dcread` and `dcwrite` are the read only and read/write community strings, respectively. All the values are user defined and can be changed at any time, but the network management system and the network devices must agree on common community strings.

1. Review the `snmpv2` section of `mgmt_vars.yml`. Set the contact to your group number. The play configure SNMP traps to be sent to the workstation.

## Task 6: Network Discovery

Objective: let the NMS find the devices.

Network discovery is one of the common functions of an NMS. An NMS software needs a starting device in the network from which it begins the network discovery process (this device is called a seed). The NMS can discover the network from this device's neighbours, routing table, and so on.

Have you noticed that LLDP is running on the devices? It is one of the sources of the neighbour information.

To allow Observium to discover the devices in the network, you will need to edit the Global Settings:

1. Go to Global Settings (under the gear icon), then Edit, then Network. Confirm that the Default SNMP version to use is v2c and change the Default SNMP communities to use to `dcread` (this is the community string that has been configured in all routers). Click Enter then Click the Save Changes button at the bottom of the page.

2. Go to Global Settings, then Edit, then Discovery. Disable `Require valid hostname` and change `Networks to permit autodiscovery` to the management network of your lab, for example `192.168.121.0/24`. This limits the discovery to the management subnet only and excludes any external devices. Save the changes.

3. Observium needs a starting point (seed) for network discovery. So, your next step is adding one device manually. Go to Add Device (under the devices icon) and enter the management address of one router (r21) in the hostname field, then click on Add Device. You do not need to enter the SNMP community string because it is the same as the global community string that was entered previously.

4. Observium performs auto discovery at regular intervals. Rather than waiting for this to happen, you can force network discovery by issuing the following command on the management workstation:

   ```bash
   docker exec observium /opt/observium/discovery.php -h all
   ```


   At the end of this process, Observium should discover all five devices in the Devices menu. Repeat the discovery command if some routers are still missing. 
   
   
5. After device discovery, Observium polls device data on regular intervals. You can start polling device data immediately.

   ```bash
   docker exec observium /opt/observium/poller.php -h all
   ```

It will take some time for Observium to collect useful sensor data, so you can use the time to answer some questions. Refer to the Observium documentation, including [https://docs.observium.org/discovery/](https://docs.observium.org/discovery/).

## Task 8: Alerts

Objective: have the NMS tell you when something is wrong.

Thus far, you had to watch the event log to see if anything had changed in the network. More practically, you need Observium to issue an alert if certain conditions are met, such as an interface being down.

1. Create an alert if an interface is down: Go to Alert Checks (under the Globe icon), then Create `New Checker`, then click on `Port` (under Select Alert Checker Entity Type). Fill the form as follows:

   ```text
   - Alert Name: Port Down
   - Message: A router port is Down
   - Test Conditions:  
      ifAdminStatus equals up  
      ifOperStatus notequals up
   - Association Ruleset: Device in \<select all five routers\>
   ```

   When done filling the form, click on the `Add Checker` button.

2. To test the alert, disable an interface in one of the router, as in the previous task:
